# Content scan slice

`bridge/content` reads evidence-rich native registry snapshots and indexes two existing static sources. It does not register content, convert assets, or prove runtime coverage. The transfer registry in `bridge/registry/content.py` is unchanged; candidate IDs here are not transferable IDs.

## Run

```powershell
py -3.12 -m tools.content.scan --sr1-export '<AssetRipper export>' --sr2-catalog 'Lab/Games/SR2/SlimeRancher2_Data/StreamingAssets/aa/catalog.json'
```

The CLI writes only metadata JSON under this worktree's ignored `Lab/GeneratedContent/content-scan/`. An explicit `--out-dir` must also be inside that ignored directory. Inputs are read only. Output rejects links/junctions at the filename and in all ancestors before resolution, uses exclusive temporary creation, flush/fsync and atomic replacement, and cleans its own temporary file on a failed publish. Existing hardlinked output files are refused before temporary creation and again before publication. Output is sorted, has no timestamps, and contains asset identifiers/hashes rather than asset bytes.

## Evidence and schema

Every scan records `realm`, source kind/hash, build label, build match, traversal completeness (`COMPLETE`, `PARTIAL`, `FAILED`), definitions and errors. Definitions preserve `native_id`, `reference_id`, `object_ref`, `is_largo`, `can_largofy`, `base_slimes`, `produced_plorts`, `prefab_refs`, appearance references, candidate `canonical_id`, mapping evidence and source evidence. The neutral IR has typed nodes, dependency edges and resolution errors.

For a runtime snapshot, pass `--sr1-runtime` or `--sr2-runtime` instead of the static source. The CLI independently hashes the active lab SR1 `Assembly-CSharp.dll` or SR2 `GameAssembly.dll`; the reader API requires an explicit `active_build` path before accepting `COMPLETE`. A snapshot's own attestation cannot replace that check. Traversal proof requires a registry identity/hash, equal expected/observed counts and unique definition references, corroborated by a separate caller-selected trusted native traversal receipt. `read_runtime_snapshot(..., traversal_anchor=receipt)` takes the receipt independently from the metadata input; the CLI accepts `--sr1-traversal-receipt` / `--sr2-traversal-receipt`. The receipt carries `realm`, `active_sha256`, `registry_identity`, `registry_sha256` and the complete unique `object_refs` list. All must agree with the independently selected build and snapshot. Reader-owned `verified_*` fields in a snapshot are ignored. No runtime receipt collector has been exercised in this slice, so a missing receipt fails closed; neither handwritten snapshots nor truncated self-reported counts are runtime proof. Schema version 1 requires `realm`, `game_build`, `completeness`, `registry_traversed`, `definitions`, and optional `errors`. Each definition requires all native relationship fields listed above plus `name` and `evidence`. A `COMPLETE` claim requires `registry_traversed: true`, a build, no errors and resolved per-definition Largo kind/eligibility/BaseSlimes shape. Native scanners must report actual prefab refs and canonical mapping evidence. This reader validates the supplied proof fields but cannot authenticate game execution on its own.

The SR1 AssetRipper reader traverses `MainSlimeDefinitions.Slimes` by GUID, resolves those YAML definitions, decodes native diet plort IDs, and follows explicit `BaseSlimes` refs. The export's match to the active patched SR1 DLL is unverified. Its appearance refs are indexed, but `LookupDirector.GetPrefab` is not traversed statically. The SR2 reader indexes Addressables definition paths; a catalogue path alone proves neither active registration nor `BaseSlimes`, eligibility or prefab. Both readers always report `PARTIAL`.

Candidate canonical base IDs are deterministic slugs from discovered metadata. They are unproven until corroborated with a runtime native mapping. Dedicated Largo relations use only explicit `BaseSlimes` refs, never a concatenated definition name. Eligible pairs are sorted, unordered, distinct and derived from observed `CanLargofy: true` base definitions. A pair is `MISSING_BOTH` only with two complete traversals, proven canonical mappings and eligibility, no conflicting claims, and absence of a dedicated definition in both registries. A native Largo requires its explicit parent relation and a dedicated prefab identity resolved by kind/hash in the asset index. Both species exclusivity and Largo absence use the same independently anchored build/traversal proof gate, and duplicate canonical mappings block exclusivity. Ambiguous, unresolved or partial evidence yields `BLOCKED_UNKNOWN`; model availability remains unknown without a dedicated asset inventory. Typed content and asset dependencies are retained as edges, including explicit unresolved nodes and cyclic graphs without recursive traversal. Portability and model extractability remain unknown until separate validation.

Outputs: `sr1-content-manifest.json`, `sr2-content-manifest.json`, and `bridge-content-manifest.json`. Generic Largo relationships remain readable by the registry APIs, but the scanner CLI does not generate Largo coverage/modeling queues; Largo design and models are maintained separately by the owner. No models or meshes are generated.

## First static input result

The actual readonly export/catalogue run found 113 SR1 linked definitions (22 bases, 91 dedicated Largos, 14 `CanLargofy` bases) and 234 SR2 catalogue definition paths (30 base, 204 Largo). SR1 YAML resolution reported 0 scan errors and indexed 113 appearance assets; SR2 reported one deliberate `CATALOG_NOT_ACTIVE_REGISTRY` limitation. The neutral IR has 460 nodes and 495 dependency edges; 200 plort edges remain unresolved because this slice does not index plort definitions, plus the catalogue limitation. Both scans remain `PARTIAL`. The 14 observed eligible SR1 bases create 91 candidate unordered pairs. All 91 are `BLOCKED_UNKNOWN`; zero qualify as `MISSING_BOTH`. The SR2 catalogue does not provide eligibility, and neither source proves a shared/exclusive native registry classification or conversion success.

Next inputs needed: native SR1/SR2 registry traversals from the parent plugins, including build identity, explicit BaseSlimes and prefab refs, plus validated canonical cross-realm mappings. Only then can full unified eligibility, shared/exclusive species and definitive missing model counts be reported.
